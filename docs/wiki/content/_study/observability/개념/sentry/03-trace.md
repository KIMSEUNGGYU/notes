# 성능 트레이싱

> 에러 수집만 켜면 관측의 세 기둥 중 트레이스 축이 통째로 빈다 (→ [세 기둥](../observability#세-기둥)).

## 1. 무엇을 수집하나

에러(터진 것)와 별개로 **안 터졌지만 느린 것**을 수집하는 기능. 값은 수집 비율(0~1) — 트랜잭션도 쿼터를 먹어서 조절이 필요하다.

**끄면 트레이스 축만 비는 게 아니다.** Web Vitals(LCP·INP·CLS)가 이 기능에 얹혀 오기 때문에, 안 켜면 사용자 체감 속도 지표까지 통째로 안 들어온다.

## 2. pageload · navigation 트랜잭션

`browserTracingIntegration` 이 루트 트랜잭션 둘을 만든다. 페이지가 처음 열리면 `pageload`, 클라이언트 라우팅으로 URL 이 바뀌면 `navigation`. 그 안에 자식 span 이 붙는다.

```
[pageload /tasks]
  ├─ resource span      스크립트·CSS·이미지
  ├─ fetch span         GET /v2/tasks
  ├─ long task          메인 스레드 50ms+ 블로킹
  ├─ long animation frame
  └─ browser metric     FP · FCP · LCP · TTFB
```

**Web Vitals 가 별도 채널이 아니라 이 트랜잭션의 일부다.** 담을 트랜잭션이 없으면 값이 갈 곳이 없다. 값에 맥락을 붙이려는 설계다 — "LCP 3.2초"만 있으면 거기서 멈추지만, 트랜잭션 안에 있으면 그 순간의 API 응답 시간이 옆에 붙어 원인까지 간다.

## 3. 샘플링 — 브라우저는 head-based 만 된다

샘플링을 정하는 시점이 둘이다.

```
head-based   시작할 때 "보낼까" 결정   →  브라우저가 쓰는 것
tail-based   끝난 뒤 "남길까" 결정      →  백엔드 collector 가 쓰는 것
```

tail-based 는 트레이스를 다 받아본 뒤 에러가 났거나 느린 것만 남긴다. 브라우저는 못 쓴다 — 판정할 중앙 collector 가 없고, 페이지가 열리는 순간 샘플링 결정을 헤더에 실어 백엔드로 내려보내야 하기 때문이다.

그래서 **프론트 샘플링은 "느린 것만 골라 남기기"가 아니라 무작위 N%** 다. 10% 면 느린 페이지 로드 열 번 중 아홉 번은 기록이 없다. p95 같은 분포 지표는 표본으로도 맞지만, 개별 사건 추적은 확률에 맡기게 된다.

비율은 트래픽으로 정한다 — **쿼터를 아끼는 문제가 아니라 표본이 통계적으로 쓸 만한가의 문제다.** 하루 20번 열리는 화면을 10% 로 받으면 이틀에 한 건이라 아무것도 못 본다. 공식 권장은 개발 100% / 프로덕션 10~20%.

## 4. 프론트와 백엔드를 잇는 것 — distributed tracing

트레이싱을 켜면 SDK 가 **모든 요청에** 헤더 둘을 실어 보낸다. 실패한 요청만이 아니라 나갈 때 미리 붙는다.

```
sentry-trace   trace ID + span ID + 샘플링 결정
baggage        샘플링 비율 등 부가 정보
```

백엔드도 Sentry 를 쓰고 있으면 같은 **trace ID** 로 자기 span 을 붙여서, 프론트 에러 하나에서 그 요청이 백엔드에서 뭘 했는지까지 이어진다.

```
[저장 실패 500]
  └─ POST /v2/tasks   3.2s
       └─ DB query    3.0s     ← 서버 구간이 붙는다
```

"프론트 문제냐 서버 문제냐"를 물어보지 않고 가른다. 백엔드가 안 쓰면 프론트 구간까지만 보이고 끊긴다.
샘플링 결정은 **최초 호출자(프론트)가 내리고 하류가 따른다** — 프론트가 20% 면 백엔드도 그 20% 만 이어진다.

## 5. 트랜잭션 이름 — 카디널리티가 여기서 반복된다

URL 이 그대로 트랜잭션 이름이 되면 작업 하나마다 줄이 하나씩 생긴다.

```
안 고치면                        고치면
/tasks/1024   1건   2.1s        /tasks/:id   3,412건   p95 2.2s
/tasks/1025   1건   1.9s
/tasks/1026   1건   2.3s
…수천 줄
```

`beforeStartSpan` 으로 `/tasks/:id` 로 정규화한다.

**같은 함정이 이 문서에서 세 번째다** — 메트릭 라벨(→ [카디널리티](../observability#카디널리티-—-메트릭의-비용)), fingerprint(→ [fingerprint](./02-fingerprint)), 그리고 트랜잭션 이름. 묶는 기준에 개별을 식별하는 값을 넣으면 안 묶인다는 한 가지 법칙이다.

## 6. INP 원인 — Long Animation Frames

INP(클릭하고 화면이 반응하기까지 걸린 시간)는 값과 원인이 다른 데이터다.

```
값     "이 버튼 INP 480ms"            모든 브라우저
원인   "validateForm() 이 320ms"     Chrome · Edge 만
```

원인을 주는 것이 **Long Animation Frames API**(LoAF). 화면 갱신이 늦어진 프레임을 관찰해 어느 스크립트가 몇 ms 를 썼는지 스크립트 단위로 귀속하고, style/layout/render 단계까지 쪼갠다. Sentry 는 `enableInp` 와 long animation frame span 으로 이걸 실어 보낸다.

| 브라우저 | LoAF |
| --- | --- |
| Chrome 123+ · Edge 123+ (2024-03) | 있음 |
| Safari · Firefox | 없음 (2026-09 확인) |

**도구를 바꿔도 해결되지 않는다** — 브라우저가 안 주는 데이터라 Datadog 이든 Grafana Faro 든 Safari 에서는 똑같이 안 나온다. 크롬 비중이 높은 관리자 도구는 거의 다 보이고, 일반 사용자용은 iOS 몫이 빈다.

이 데이터는 발생한 순간에만 존재하고 페이지를 닫으면 사라진다. 개발자 도구로도 같은 값을 보지만 **내 PC 에서 재현될 때만** 보이고, 480ms 는 저사양 기기에서만 나므로 대개 재현이 안 된다. 수집 도구가 하는 일은 값을 만드는 게 아니라 **흩어져 사라지는 값을 모아 검색 가능하게 만드는 것**이다.
