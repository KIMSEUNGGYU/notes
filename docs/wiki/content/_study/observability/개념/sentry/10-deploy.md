# 배포 연결

배포하면 코드가 변형되고 여러 환경으로 나간다. 그래서 이벤트가 왔을 때 세 가지를 모른다.

```
어느 줄에서 났나     압축돼서 a.js:1:38271 로 보인다       →  소스맵
어느 배포에서 났나   번들이 매번 바뀐다                     →  release
어느 환경에서 났나   local · dev · live 가 섞여 들어온다    →  environment
```

셋 다 **배포된 코드와 Sentry 이벤트를 잇는 역할**이라 한 묶음이다. 서로 물려 있기도 하다.

```
소스맵을 고르려면  →  release 가 있어야 한다 (빌드마다 소스맵이 다르니까)
목록을 볼 때        →  environment 로 걸러야 한다 (dev 에러가 섞이면 못 본다)
```

## 1. 소스맵 — 압축된 위치를 원본으로

배포된 코드는 용량을 줄이려고 압축·난독화된다. 되돌릴 수 없게 만든 것이 아니라 이름을 짧게 바꾼 것이라, **대응표만 있으면 복원된다.** 그 대응표가 소스맵이다.

```
소스맵 없음
  at t (a.js:1:38271)
  at n (a.js:1:12043)

소스맵 있음
  at HttpClient.request (src/lib/HttpClient.ts:88:15)
  at saveTask (src/api/task.ts:31:7)
```

위쪽으로는 아무것도 못 한다. 한 줄짜리 번들에서 38271번째 글자가 어느 코드인지 알 수 없다.

Next.js 는 `next.config.ts` 의 `withSentryConfig` 가 빌드 때 자동으로 업로드한다.

## 2. release — 어느 빌드에서 났나

"이 이벤트가 어느 배포에서 났나"를 나타내는 문자열. 커밋 해시나 버전을 쓴다.

```
release: "a3f21c8"   또는   "1.4.2"
```

붙으면 세 가지가 된다.

```
소스맵 매칭               이 이벤트에 맞는 소스맵을 고른다
언제부터 났나              이슈 상세에 "first seen in a3f21c8"
Resolve in next release   그 배포가 나갈 때까지는 regression 으로 안 친다
```

세 번째는 그냥 resolve 와 다르다. 배포 전에 온 이벤트로는 되살아나지 않는다 (→ [이슈 라이프사이클](./09-lifecycle)).

## 3. environment — 어느 환경에서 났나

이벤트에 붙는 환경 구분. **기억용이 아니라 가르는 용도**다.

```
목록에서   dev 에서 난 에러를 빼고 본다
알림에서   live 에서만 알림을 받는다
```

없으면 개발하면서 낸 에러가 실사용자 에러와 같은 목록에 섞인다. 그러면 목록을 못 믿게 되고 결국 아무도 안 보게 된다.

제약이 있다 — **64자 이내이고 공백·줄바꿈·슬래시와 문자열 `None` 을 못 쓴다. 대소문자를 구분한다.**

## 4. 없으면 티가 나는 것과 안 나는 것

```
소스맵    없으면 바로 티가 난다      stack trace 가 못 읽는 문자열로 나온다
release   없어도 티가 안 난다        기능이 안 보일 뿐이라 아쉬운 줄도 모른다
```

release 가 없으면 "이 배포부터 났다"를 못 보고, 소스맵 매칭도 위태로워진다. 다만 **없다는 사실 자체가 드러나지 않는다** — 그래서 한 번 확인해봐야 하는 값이다.

확인하는 법은 간단하다. **Sentry 이슈를 하나 열면 둘이 한 번에 판별된다** — stack trace 가 `.ts` 파일로 보이는지(소스맵), 오른쪽에 release 값이 붙어 있는지.
