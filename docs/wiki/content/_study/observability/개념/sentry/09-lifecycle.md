# 이슈 라이프사이클

## 1. 목록에서 치우는 길 둘

```
resolve   "고쳤다"        → 한 건만 다시 나도 되살아난다
archive   "안 고칠 거다"   → 고른 조건에 걸리면 되살아난다. 알림은 꺼진다
```

**둘 다 "내가 안 봐도 Sentry 가 다시 꺼내준다"는 장치다.** 그래서 목록을 비우는 게 중요하다 — 다 열어두면 진짜 봐야 할 것이 안 보이는데, 닫아두면 필요할 때 알아서 돌아온다.

```
resolve  →  Regressed    고쳤다고 했는데 또 난다
archive  →  Escalating   안 고쳐도 된다고 했는데 커졌다
```

예민함이 다르다. resolve 는 한 건에도 반응하고("고쳤으니 한 건도 나면 안 된다"), archive 는 평소보다 늘어야 반응한다("원래 나던 거니까 늘어야 의미 있다"). **안 고칠 것을 resolve 하면 매번 되살아나 목록이 안 비워진다.**

## 2. 상태 여섯

그중 넷이 `is:unresolved` 에 든다 — 되살아난 둘(Escalating · Regressed)이 자동으로 목록에 다시 뜨는 구조라, 묻어둔 것을 주기적으로 확인할 필요가 없다.

```
New ─▶ Ongoing ─┬─ resolve ──▶ Resolved ── 새 이벤트 ──▶ Regressed
                │                                          (자동 재오픈)
                ├─ archive ──▶ Archived ── 이벤트 급증 ──▶ Escalating
                │                                          (자동 재오픈)
                └────────────────────────▶ Escalating

is:unresolved 에 드는 것 — New · Ongoing · Escalating · Regressed
```

- **New / Ongoing** — 갓 생긴 이슈와 계속 나고 있는 이슈. 가르는 기준은 아래에서 다룬다
- **Resolved** — "고쳤다"는 표시. 목록 기본 필터에서 사라진다. 배포로 고친 건 "Resolve in next release"로 버전과 묶을 수 있다 (release 설정 필요)
- **Regressed** — resolve된 이슈에 같은 fingerprint 이벤트가 다시 오면 자동으로 되살아난다. "고쳤다고 믿었는데 재발"을 잡는 장치
- **Archived** — 알림을 끄고 목록에서 내린다. 되살아날 조건은 아래에서 고른다
- **Escalating** — 이슈가 **예측된 발생량을 넘겼을 때** 자동으로 붙는 상태. 묻어둔 이슈가 갑자기 커지면 여기로 올라온다

**Regressed와 Escalating은 다르다** — 앞은 "고쳤다고 한 게 재발", 뒤는 "안 고친 게 갑자기 심해짐"이다.

## 3. archive 는 언제 깨울지를 고른다

```
급증하면 (기본)      평소보다 확 늘면 깨운다
N일 뒤              시간이 지나면 깨운다
N건 더 나면          횟수로 깨운다
N명이 더 겪으면       영향 범위로 깨운다
영원히               안 깨운다        ← 이것만 진짜 못 본다
```

"영원히"를 써도 되는 경우는 거의 없다. 정말 우리 손을 떠난 것 정도다.

```
브라우저 확장 프로그램이 던지는 에러
서비스를 접은 옛 페이지의 에러
```

그런데 **이런 건 애초에 안 받는 게 낫다.** `denyUrls` 나 Inbound Filters 로 막으면 쿼터도 안 먹는다 (→ [거르는 방법](./08-quota#_2-거르는-방법-—-sentry-가-주는-넷)). archive 는 이미 받은 뒤라 쿼터는 나간 상태다.

그래서 **"영원히"는 대개 잘못된 선택의 신호다.** 묻고 싶어졌다면 왜 받고 있는지를 먼저 물어야 한다.

## 4. Escalating 은 지난주와 비교해 정한다

임의 기준이 아니라 **이슈마다 따로 계산한다** (2026-09-09 공식 문서 확인).

```
지난 7일 데이터로  →  다음 주의 일별 한도를 계산  →  넘으면 Escalating
```

한도는 두 식으로 각각 구해 **더 큰 쪽**을 쓴다.

```
spike limit    평소 양이 안정적인 이슈용    시간당 가중 평균 + 표준편차
bursty limit   원래 몰아서 터지는 이슈용    시간당 최대량 + 변동계수
```

정기 배치처럼 원래 특정 시간에 몰리는 이슈가 매번 급증으로 뜨지 않게 하려는 설계다. 7일치가 없는 새 이슈는 `시간당 최대량 × 10` 으로 잡는다.

**전역 threshold 로는 이걸 못 잡는다.** "시간당 50건 넘으면"을 걸면 원래 많이 나는 이슈가 계속 울리고, 조용하던 이슈가 열 배로 뛴 것은 놓친다.

한계 — merge/unmerge 한 이슈에는 동작하지 않는다.

## 5. New 는 7일

발생량이 아니라 **시간** 기준이다.

```
New       생성된 지 7일 이내
Ongoing   7일이 지났거나, 사람이 "검토함"으로 표시했거나
```

수동으로 reviewed 를 누르면 7일 안이라도 Ongoing 이 된다. 검색은 `is:new` · `is:ongoing`.

New 의 쓸모는 **분류**다. 지난 일주일에 새로 생긴 것만 훑고 본 것은 reviewed 로 넘기면 목록이 비워진다. 우아한형제들의 "스프린트마다 2~3명 당번이 검토완료 표시"가 이 흐름이다 (→ [알림 피로](./05-alert)).

## 6. resolve 가 의미를 가지려면

이슈가 잘 갈려 있어야 한다. 뭉쳐 있으면 이렇게 된다.

```
ApiError 이슈 하나에 결제·저장·로그인 실패가 섞여 있다
  → 결제를 고치고 resolve
  → 다음 날 로그인 실패가 들어옴
  → 같은 fingerprint 라 Regressed 로 되살아남
```

고친 건 맞는데 다른 원인이 되살린다. **resolve 가 거짓말이 된다.** fingerprint 가 엔드포인트별로 갈리면 결제 이슈만 닫히고 로그인은 자기 이슈에 남는다 (→ [fingerprint](./02-fingerprint)).
