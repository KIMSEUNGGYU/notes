# 알림

## 1. 알림 피로 — 많이 걸면 없는 것과 같아진다

알림은 거는 것보다 **누가 보는가**가 절반이다. 안 보는 알림은 안 건 알림과 같다.

알림이 죽는 전형적인 순서:

1. 걸 수 있는 조건을 다 건다
2. 채널에 하루 수백 건이 쌓인다
3. 사람이 스크롤로 넘긴다
4. 진짜 장애 알림도 같이 넘어간다

막는 장치들:

- **threshold** — "1건이라도 나면"이 아니라 "시간당 N건 넘으면". 개별 에러는 목록에서 보고, 알림은 급증만 받는다
- **그룹핑이 선행 조건** — 이슈가 뭉쳐 있으면 "에러 급증" 알림이 어느 기능인지 안 알려줘서 열어봐야 안다. 이슈가 잘 갈린 뒤에야 "이 API 급증" 알림이 의미를 갖는다
- **채널 라우팅** — 서비스별·심각도별로 채널을 가른다. 한 채널에 다 쏟으면 아무도 자기 것으로 안 본다
- **당번** — 스프린트마다 2~3명을 정해 "본 것"을 표시하게 한다. 주인이 없으면 전원이 남의 일로 본다

알림에 쓸 수 있는 건 **인덱싱된 축**뿐이다. 검색·필터가 되는 태그로 남겨야 알림 조건에 쓸 수 있고, 이벤트 본문에만 넣은 값은 열어봐야 보인다. **어떤 값을 태그로 올릴지가 곧 어떤 알림을 걸 수 있는지를 정한다.**

## 2. Sentry 에서 알림 걸기

이슈·이벤트 조건에 맞으면 Slack 등으로 보내는 규칙. 조건에 태그 필터(`service:admin`)와 threshold(시간당 N건 이상)를 걸 수 있다.

**fingerprint 정리가 선행 조건이다** — 이슈가 뭉쳐 있으면 "ApiError 급증" 알림은 어느 API인지 안 알려줘서 의미가 없다. 이슈 = 엔드포인트가 된 뒤에야 "특정 API 급증" 알림이 가능하다.

우아한형제들 운영: threshold + Slack 채널 라우팅 + 스프린트마다 2~3명 당번 + "검토완료" 버튼. (→ [Observability §알림 피로](#_1-알림-피로-—-많이-걸면-없는-것과-같아진다))

## 3. 검색·쿼리 문법 — 알림 조건과 같은 축

Issues 목록 상단 검색창에서 쓰는 문법. **태그와 내장 속성만 검색되고 extra·context는 안 된다.**

```
is:unresolved                      상태 필터 (is:resolved, is:regressed)
service:partners                   태그 필터 (직접 붙인 태그 그대로)
api.endpoint:/v2/tasks             태그 필터
error.type:TimeoutError            에러 클래스명
message:*modusign*                 메시지 와일드카드
```

조건은 공백으로 이어 붙이면 AND다:

```
error.type:TimeoutError message:*modusign* service:partners
```

**여기서 쓸 수 있는 축이 곧 알림 조건으로 쓸 수 있는 축이다.** 무엇을 태그로 올릴지가 무엇을 셀 수 있는지를 정한다.
