# 보안 그룹과 체이닝

> 이 문서의 질문: **누가 어디로 들어올 수 있는지를 어떻게 통제하나?**

## 1. 최소 권한 원칙 (PoLP)

**PoLP(Principle of Least Privilege)** = 꼭 필요한 만큼만 허용하고 나머지는 전부 막는다.

예를 들어 ALB의 443을 전 세계(`0.0.0.0/0`)에 열지 않고 접속이 필요한 특정 IP만 허용한다. **열어둔 만큼이 공격 표면**이라, 최소로 줄이면 사고 시 피해도 최소가 된다.

## 2. 보안 그룹 — 리소스 앞의 문지기

**SG** = 리소스(서버·DB·ALB) 앞을 지키는 문지기이자 **입장 허용 명단**. "어떤 출발지가 어떤 포트로 들어와도 되는지"를 적어둔 것이다.

비유하면 클럽 입구 가드 + 입장 명단이다. **명단에 있으면 들이고, 없으면 막는다** — deny를 따로 안 적어도 "명단에 없음 = 못 들어옴"이다.

**리소스마다 따로 붙는다** — VPC도 서브넷도 아니라 **각 리소스의 ENI**에 붙는다. EC2 인스턴스, ECS Fargate task(task마다 ENI+IP), ALB, RDS 각각에. 그래서 같은 서브넷이어도 리소스마다 다른 SG를 쓸 수 있다.

```
무엇    리소스 앞 방화벽 — "누가 들어올 수 있나" 검문
어디    각 리소스(ALB·앱 task·RDS)의 ENI에 따로
규칙    방향(인/아웃) + 포트 + 출발지(CIDR 또는 다른 SG)
성질    allow만 (없으면 차단) · stateful (응답 자동) · 리소스 단위
```

## 3. stateful — 연결을 기억한다

가장 헷갈리는 개념. **stateful = 방화벽이 "이 연결은 내가 허락해서 시작된 거야"를 기억하는 것.** 그래서 그 연결의 **응답은 규칙을 다시 안 보고 자동 통과**한다.

```
stateful  (SG)    손님이 들어올 때 확인 + 얼굴 기억 → 나갈 땐 안 막는다
stateless (NACL)  기억 안 함 → 들어올 때·나갈 때 둘 다 확인. 응답용 규칙도 따로 적어야 한다
```

구체적으로, 웹서버 SG에 "인바운드 443 허용"만 적었다고 하자:

```
외부가 443으로 들어옴        → 인바운드 규칙 통과 ✅
서버가 응답을 돌려보냄(나감)  → 아웃바운드 규칙에 안 적어도 자동 통과
                              (SG가 "아까 그 연결의 응답"이라고 기억하니까)
```

HTTP로 보면 **인바운드 = 요청 받기**이고, 응답은 그 요청에 딸린 것이다. **요청을 허용하면 응답은 따로 안 열어도 나간다.** 그러니 정할 건 **연결의 시작 방향** 하나뿐이다.

이 성질이 [SSM이 인바운드 0으로도 동작하는](./04-bastion-ssm#_5-왜-인바운드-0인데-양방향이-되나) 이유이기도 하다.

## 4. 인바운드 / 아웃바운드

```
인바운드 규칙   이 리소스로 들어오려는 연결을 누가/어느 포트로 할 수 있나
아웃바운드 규칙  이 리소스가 나가는 연결을 어디로 할 수 있나
```

보통 **인바운드를 빡빡하게** 잡고(누가 들어오나가 위험하니까) 아웃바운드는 느슨하게 둔다.

## 5. 규칙의 생김새 = 방향 + 포트 + 출발지

규칙 하나 = **(인/아웃)** + **(프로토콜·포트, 예 `tcp 443`)** + **(출발지)**.

출발지는 둘 중 하나다:

```
CIDR (IP 범위)   10.2.0.0/16, 특정 1.2.3.4/32
다른 SG          "앱 SG에서 오는 것" = 그 SG를 달고 있는 리소스에서 오는 것
                 서브넷·IP 위치와 무관하다. SG 멤버십 = 신분증
```

**두 번째가 체이닝의 재료다.** IP가 바뀌어도 SG만 같으면 통과한다.

## 6. SG 체이닝 — 계층 방화벽

**SG 체이닝** = 각 계층의 SG가 "**바로 앞 계층의 SG에서 온 것만**" 인바운드 허용하도록 줄줄이 연결하는 것.

출발지를 IP가 아니라 앞 단계의 SG(신분증)로 지정하면 계층이 사슬처럼 이어진다.

```
[외부 허용 IP] ──443──▶ [ALB SG] (public-lb-dev-sg)
                           │  허용 출발지 = "ALB SG"
                           ▼
                        [앱 SG] (private-dev-sg)
                           │  허용 출발지 = "앱 SG"
                           ▼
                        [DB SG] (private-dev-db-sg, 3306)
```

- **ALB SG**: 443 ← 허용 IP 목록만 (`0.0.0.0/0`이 아니다 = PoLP)
- **앱 SG**: ← **ALB SG에서** 온 것만 (ALB를 거친 것만 앱에 닿는다)
- **DB SG**: 3306 ← **앱 SG에서** 온 것만 (앱을 거친 것만 DB에 닿는다)

외부에서 DB로 직접? 불가능. 앱으로 직접? 불가능(ALB를 거쳐야 한다). **한 단계씩만** 통과한다.

### 검사는 도착지에서, 직전만 본다

검사는 **도착지 계층의 인바운드**에서 일어난다 — `ALB→앱`이면 **앱 SG**가 "출발지가 ALB SG냐"를 검사한다.

```
허용 IP ─▶ ALB   (ALB SG: 허용 IP만)
            └─▶ 앱   (앱 SG: ALB SG에서만)
                 └─▶ DB  (DB SG: 앱 SG에서만)   ← 도착지 SG가 "직전 계층 SG냐"만 검사
```

**DB는 앱 SG에서만 받지 ALB SG는 안 본다.** 그래서 ALB가 DB로 직접 갈 수 없고 반드시 앱을 거쳐야 한다 — 건너뛰기가 구조적으로 막힌다.

### 왜 IP 대신 SG로 묶나

- **IP는 바뀐다** — 특히 Fargate task는 뜰 때마다 IP를 새로 받는다. IP로 적으면 매번 규칙을 고쳐야 한다
- **SG(신분증)는 안 바뀐다** — "앱 SG 단 애들"이라고 적으면 task IP가 바뀌어도 **그 SG만 달려 있으면 자동 허용**된다. 유지보수 0
- **의미도 명확하다** — "앱에서 DB로"가 IP 나열보다 읽기 쉽다

## 7. 이중 차단 — 망분리의 실제 구현

지금까지 배운 게 여기서 합쳐진다:

```
1차  서브넷/라우팅   DB·앱은 private 서브넷 → 외부에서 라우팅상 직접 못 들어간다
2차  SG 체이닝       그 위에 "앞 계층에서 온 것만" → 안에 들어와도 계층을 못 건너뛴다
```

**두 겹 방어**다. 망분리를 하겠다는 말의 실제 구현이 이 조합이다.

## 8. NACL — 서브넷 단위 방화벽

**NACL(Network ACL)** = 서브넷 단위 방화벽. SG는 리소스 하나하나에, NACL은 서브넷 전체에 한 겹 더 얹는다.

비유하면 **SG = 각 사무실 문 잠금, NACL = 건물 정문 한 겹**이다.

| | 보안 그룹(SG) | NACL |
|---|---|---|
| 단위 | **리소스**(ENI) | **서브넷** |
| 상태 | **stateful** (응답 자동) | **stateless** (응답도 따로 허용) |
| 규칙 | allow만 | allow + **deny** |

보통 **SG로 충분하다.** NACL은 "이 서브넷에 이 IP 대역 통째 차단" 같은 광범위 처리의 보조다.

## 9. 확인하는 법

```bash
# VPC의 SG 목록
aws ec2 describe-security-groups --filters "Name=vpc-id,Values=<VPC_ID>" \
  --query "SecurityGroups[].[GroupId,GroupName]" --output table

# 특정 SG의 인바운드 규칙 (포트 + 출발지: cidr 또는 srcSG)
aws ec2 describe-security-groups --group-ids <SG_ID> \
  --query "SecurityGroups[].IpPermissions[].{proto:IpProtocol,from:FromPort,to:ToPort,cidr:IpRanges[].CidrIp,srcSG:UserIdGroupPairs[].GroupId}" --output json
```

`srcSG`가 앞 계층 SG를 가리키면 체인이 이어진 것이다. ALB SG의 443이 특정 IP만이고 DB SG의 3306이 앱 SG에서만이면 PoLP + 체이닝이 둘 다 서 있다.

## 한 줄 정리

- **PoLP** = 꼭 필요한 만큼만 허용. **SG** = 리소스 앞 문지기(허용 명단), 명단에 없으면 자동 차단
- **stateful** = 연결을 기억한다 → 시작 방향만 정하면 응답은 자동 통과
- 규칙 = **방향 + 포트 + 출발지(CIDR 또는 SG)**
- **SG 체이닝** = 출발지를 앞 계층 SG로 지정 → 각 계층은 직전에서만 받는다. IP가 변해도 유지보수 0
- **private 서브넷 + SG 체이닝 = 이중 차단 = 망분리**
