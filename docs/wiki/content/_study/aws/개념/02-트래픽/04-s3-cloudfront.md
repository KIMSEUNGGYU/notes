# S3와 CloudFront

## S3 — 파일 저장 서비스

> 한 줄 요약: **파일 저장에 특화된 서비스.** 저장뿐 아니라 다운로드도 최적화돼 있다.

이미지 업로드 기능을 만들면 파일을 어디 둘지 정해야 한다. EC2 내부에 저장할 수도 있지만, 운영하다 보면 파일이 쌓여 서버가 지저분해지고 서버가 죽으면 파일도 같이 간다. 그래서 파일은 S3에 둔다.

### 업로드 흐름 — DB에 저장되는 건 파일이 아니라 URL

```
① 클라이언트 → 서버로 이미지 전송
② 서버 → S3에 업로드
③ S3 → 저장된 파일의 URL 응답
④ 서버 → 그 URL을 DB(RDS)에 저장
```

흔한 오해 하나: 이미지 파일 자체를 DB에 넣는 게 아니다. **파일은 S3에, DB엔 그 파일을 가리키는 주소만** 들어간다.

### S3는 정적 웹사이트 호스팅도 한다

파일 저장 외에 **정적 웹사이트 호스팅** 기능이 있다. 빌드된 HTML·CSS·JS를 올려두면 웹으로 서빙된다. 다만 한계가 있는데, 그게 CloudFront를 부른다.

## CloudFront — CDN

> 한 줄 요약: **콘텐츠를 빠르게 전송하게 해주는 서비스.**

S3가 한국에 있다면 한국 사용자는 가깝지만, 미국 사용자는 멀어서 전송이 느리다.

해결책은 **전 세계 곳곳에 콘텐츠 복사본을 두는 임시 저장소(엣지 로케이션)** 다. 미국 사용자는 미국에서 가장 가까운 저장소에서 받는다. 이런 형태의 서비스를 **CDN(Content Delivery Network)** 이라 하고, CloudFront가 AWS의 CDN이다.

```
유저 → CloudFront(가까운 엣지)
         ├ 캐시에 있으면      → 바로 응답 (S3 안 감)
         └ 캐시에 없으면      → S3에서 가져와 응답 + 캐시에 저장
```

캐시가 이 구조의 핵심이라, **캐시 무효화(invalidation)** 라는 개념이 따라온다 — 파일을 교체했는데 엣지에 옛 캐시가 남아 있으면 사용자는 옛것을 본다.

### S3와 CloudFront를 같이 쓰는 이유

성능도 있지만 결정적인 건 **HTTPS**다.

**S3의 정적 웹사이트 호스팅은 HTTPS를 지원하지 않는다.** 그래서 S3 단독으로는 제대로 된 웹 서비스를 배포할 수 없고, CloudFront를 앞에 두어 HTTPS를 입힌다. 보안도 한 겹 강화된다(S3를 직접 노출하지 않는다).

정리하면 CloudFront를 쓰는 이유 셋: **① 전송 속도 ② HTTPS ③ S3 직접 노출 차단.**
