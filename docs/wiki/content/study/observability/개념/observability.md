# Observability

> 밖에서 보이는 신호만으로 안에서 무슨 일이 났는지 답할 수 있는가.

## 모니터링과 관측의 차이

**모니터링** — 미리 정한 질문에 답한다. "5xx가 분당 10건 넘었나", "LCP p75가 2.5초를 넘었나". 질문을 알고 있으니 대시보드와 알림을 미리 만들어 둔다.

**관측** — 미리 안 정한 질문에도 답한다. "어제 3시에 특정 안드로이드 크롬 버전 사용자만 제출이 실패했는데 왜지". 이 질문은 어제 3시 전에는 존재하지 않았다.

차이는 도구가 아니라 **남긴 데이터의 모양**에 있다.

```
집계해서 수만 남긴다        → 나중에 어느 축으로도 못 쪼갠다 (싸다)
사건마다 맥락을 붙여 남긴다  → 나중에 아무 축으로나 쪼갠다 (비싸다)
```

프론트엔드에서 이 차이가 나오는 자리:

- 에러율 그래프만 있으면 "올랐다"까지만 안다
- 에러 이벤트마다 브라우저·기기·API 경로·직전 행적이 붙어 있으면 "이 브라우저에서 이 API만"까지 간다

"관측 가능하게 만든다"는 대개 **후자를 쪼갤 수 있는 축으로 남기는 일**이지, 도구를 하나 더 붙이는 일이 아니다.

## 세 기둥

### 로그 — 사건 하나를 시간순으로

무슨 일이 언제 났는지를 문장 단위로 남긴다.

```
14:23:01  POST /v2/tasks/1024 → 400 {"code":"INVALID_STATE"}
14:23:01  ErrorBoundary caught: ApiError: 진행중 상태에만 저장 가능합니다
14:23:04  user clicked "다시 시도"
```

- **답하는 것** — "이 사용자 한 명에게 무슨 순서로 무슨 일이 났나"
- **못 답하는 것** — "전체에서 몇 번 났나". 세려면 전부 읽어야 한다
- **비용** — 양에 비례. 사용자가 늘면 그대로 늘어난다

프론트엔드에서는 에러 수집 도구의 breadcrumbs가 이 역할을 한다. 클릭·페이지 이동·네트워크 요청이 자동으로 쌓여 있어, 에러 하나를 열면 그 직전 행적이 로그처럼 읽힌다.

### 메트릭 — 수를 세서 추이로

미리 정한 축으로 집계한 수를 시간에 따라 남긴다.

```
page_error_total{service="admin", browser="chrome"}  분당 12건
web_vitals_lcp_p75{page="/tasks"}                    2.8s
```

- **답하는 것** — "지금 정상인가", "어제보다 나빠졌나". 값이 가벼워서 오래 보관하고 빨리 그린다
- **못 답하는 것** — "그 12건 중 하나를 열어보자". 개별 사건이 이미 사라졌다
- **비용** — 사용자 수와 무관. **라벨 조합 수에 비례한다** (아래 카디널리티)

알림을 거는 대상은 거의 항상 메트릭이다. 로그로 알림을 걸면 "몇 건인가"를 매번 세야 한다.

### 트레이스 — 요청 하나가 지나간 길

한 번의 사용자 동작이 어느 구간에서 얼마를 썼는지 구간(span)으로 쪼갠다.

```
[페이지 진입 /tasks]                             1420ms
  ├─ [GET /v2/tasks]                    820ms
  │    └─ [DB query]              610ms
  ├─ [GET /v2/me]                        90ms
  └─ [렌더]                             180ms
```

- **답하는 것** — "느린데 어디가 느린가". 프론트가 느린지 API가 느린지 DB가 느린지가 한 줄로 갈린다
- **못 답하는 것** — 안 터지고 안 느린 것은 안 본다. 그리고 **비용 때문에 표본만 수집**한다(샘플링)
- **비용** — 요청 수 × 샘플링 비율. 100% 수집은 대개 감당이 안 된다

에러 수집만 켜 두면 이 축이 통째로 빈다 — "안 터졌지만 느린 것"이 하나도 안 남는다.

### 셋 중 뭘 켤까


| 질문                  | 답하는 기둥       |
| ------------------- | ------------ |
| 터졌나 / 무슨 순서로 터졌나    | 로그 (+ 에러 수집) |
| 지금 정상인가 / 언제부터 나빠졌나 | 메트릭          |
| 느린데 어디가 느린가         | 트레이스         |
| 사람들이 이 버튼을 쓰나       | 행동 로그 (아래)   |


**행동 로그는 관측이 아니라 제품 분석에 가깝다.** GA·Mixpanel로 보내는 클릭 이벤트는 "장애가 났나"가 아니라 "제품이 팔리나"에 답한다. 같은 `logger` 라는 이름을 쓰지만 목적이 다르고, 그래서 **끊겨도 아무도 안 죽는다** — 이 둘을 같은 신뢰도로 다루면 안 되는 이유다.

## 카디널리티 — 메트릭의 비용

메트릭 하나가 가질 수 있는 **라벨 조합의 수**. 조합마다 시계열이 하나씩 생기고, 저장·조회 비용은 시계열 개수에 비례한다.

```
http_requests_total{method, status}
  → method 5 × status 6 = 30 시계열

여기에 user_id 를 붙이면
  → 30 × 사용자 수 = 사용자 10만이면 300만 시계열
```

라벨은 **더해지는 게 아니라 곱해진다.** 그래서 "혹시 몰라 붙여두자"가 메트릭에서는 사고가 된다.

붙이면 안 되는 라벨 — 값의 가짓수가 무한히 늘어나는 것:

- `user_id`, `session_id`, `request_id`
- 정규화 안 한 URL (`/tasks/1024`, `/tasks/1025` … → `/tasks/:id` 로 치환)
- 에러 메시지 원문 (백엔드 문장이 바뀌면 새 시계열)

**이 셋은 메트릭이 아니라 로그·트레이스에 실어야 한다.** 개별 사건을 특정하는 값은 개별 사건을 남기는 기둥의 몫이다.

같은 함정이 에러 그룹핑에도 있다 — 이슈를 가르는 키에 ID를 그대로 넣으면 ID마다 이슈가 새로 생겨 목록이 폭발한다. (→ [Sentry 의 fingerprint](./sentry#_2-fingerprint-—-이슈-그룹핑-키))

## SLO와 에러버짓

"무엇을 얼마나 지킬 건가"를 숫자로 정하는 것. 관측 데이터를 **판단**으로 바꾸는 층이다.

```
SLI  측정하는 값        예) 성공 응답 비율
SLO  지키기로 한 목표    예) 30일간 99.9%
에러버짓  허용된 실패량   예) 100% - 99.9% = 0.1%
```

99.9%가 30일이면 허용 실패 시간은 **43분**이다. 99.99%면 4분 20초.

에러버짓이 쓸모 있는 이유는 **"장애가 났다"를 참/거짓이 아니라 잔액으로 바꾸기 때문**이다.

- 버짓이 남았다 → 배포 속도를 유지한다. 작은 에러는 감수한다
- 버짓을 다 썼다 → 기능 배포를 멈추고 안정화에 쓴다

목표를 100%로 잡으면 이 장치가 죽는다. 100%는 달성 불가능해서 항상 위반 상태가 되고, 그러면 아무 신호도 안 남는다. **일부러 여유를 남기는 숫자**여야 판단이 가능하다.

## 알림 피로

알림은 거는 것보다 **누가 보는가**가 절반이다. 안 보는 알림은 안 건 알림과 같다.

알림이 죽는 전형적인 순서:

1. 걸 수 있는 조건을 다 건다
2. 채널에 하루 수백 건이 쌓인다
3. 사람이 스크롤로 넘긴다
4. 진짜 장애 알림도 같이 넘어간다

막는 장치들:

- **threshold** — "1건이라도 나면"이 아니라 "시간당 N건 넘으면". 개별 에러는 목록에서 보고, 알림은 급증만 받는다
- **그룹핑이 선행 조건** — 이슈가 뭉쳐 있으면 "에러 급증" 알림이 어느 기능인지 안 알려줘서 열어봐야 안다. 이슈가 잘 갈린 뒤에야 "이 API 급증" 알림이 의미를 갖는다
- **채널 라우팅** — 서비스별·심각도별로 채널을 가른다. 한 채널에 다 쏟으면 아무도 자기 것으로 안 본다
- **당번** — 스프린트마다 2~3명을 정해 "본 것"을 표시하게 한다. 주인이 없으면 전원이 남의 일로 본다

알림에 쓸 수 있는 건 **인덱싱된 축**뿐이다. 검색·필터가 되는 태그로 남겨야 알림 조건에 쓸 수 있고, 이벤트 본문에만 넣은 값은 열어봐야 보인다. **어떤 값을 태그로 올릴지가 곧 어떤 알림을 걸 수 있는지를 정한다.**
